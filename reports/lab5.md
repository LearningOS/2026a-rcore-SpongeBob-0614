# 第八章实验报告：死锁检测

分支：`ch8`　日期：2026 年 11 月 9 日

## 功能总结

给互斥锁和信号量加上死锁检测。申请资源时检查当前的分配和等待关系，发现死锁就拒绝请求，返回 `-0xDEAD`。进程可以通过 `enable_deadlock_detect` 开关检测。另外补齐了 `sys_get_time`，支持跨页写回时间。

## 实现说明

每个进程在 PCB 里保存检测状态，互斥锁和信号量各用一份 `ResourceTracker`。其中，`Available` 是剩余资源数，`Allocation` 是各线程已经拿到的资源，`Need` 是当前的等待请求。互斥锁初始有 1 份资源，信号量按创建时的数量初始化。新建资源时补一列；线程退出或 TID 复用时，清空对应行。

检查用的是题目给出的算法。先把这次请求加到 `Need`，复制 `Available` 得到 `Work`，再找需求能被 `Work` 满足的线程。假设这个线程运行结束，把它持有的资源加回 `Work`，接着找下一个。能让所有线程依次完成，就接受请求；找不到这样的顺序，就撤销刚加的请求，返回错误。真正取得资源时，才减少 `Available`、增加 `Allocation`。

阻塞锁解锁或信号量执行 `up` 时，如果有线程等待，就先把资源转给队首线程，再唤醒它。记录更新放在同步原语内部，条件变量等待时的解锁、重新加锁也走这套逻辑。重新加锁被拒绝时，`condvar_wait` 返回 `-0xDEAD`。

检测开关只接受 0 和 1，其他参数返回 `-1`。关闭检测后仍然记账，重新开启时可以继续使用已有状态。线程退出也不会自动替它解锁或执行 `up`，持有的资源需要在线程退出前归还。

检测范围按题目要求限制在同类资源内，不检查互斥锁、信号量和 `waittid` 混合形成的死锁。前章代码只迁入时间查询，其余沿用 ch8 框架。

## 问答

### 1. 主线程退出时，需要回收哪些资源？TCB 还可能被哪些位置引用？

0 号线程退出时，整个进程都要结束。需要回收所有线程的用户栈、trap context 和 TID，释放进程共享的用户页面，关闭文件描述符，清理同步对象和检测记录。内核栈随 TCB 一起释放，当前正在使用的栈要留到任务切换后再回收。

回收顺序不能颠倒。用户栈和 trap context 由 `TaskUserRes` 管理，先析构它们，再回收整个地址空间，避免重复撤销映射。析构 `TaskUserRes` 时还会访问 PCB，所以代码先把资源取出来，放开 PCB 的可变借用，再统一释放。

TCB 通过 `Arc` 引用，清空线程表只会减少一处引用。还要检查下面这些位置：

| 位置 | 退出时的处理 |
| --- | --- |
| PCB 的 `tasks` | 清空线程表。 |
| 调度器的就绪队列 | 删除对应线程，防止它再次被调度。 |
| 定时器堆 | 删除睡眠记录，防止到期后再次唤醒该线程。 |
| 互斥锁、信号量、条件变量的等待队列 | 释放队列持有的引用。这些同步对象只在进程内使用，可随对象销毁一起清理。 |
| 处理器当前任务、退出时的临时变量和 `stop_task` | 先取出当前任务；主线程的内核栈还在使用，暂由 `stop_task` 保留，切换后才能释放。 |

TCB 对所属进程使用 `Weak` 引用，不会阻止 PCB 回收。PCB 的退出码还要留给父进程的 `waitpid` 读取，所以进程退出后，PCB 不会立刻销毁。

### 2. 题目中的两种 Mutex 实现有什么区别？可能出现什么问题？

`Mutex1` 解锁时先把 `locked` 设为 `false`，再唤醒队首线程。这个线程醒来后回到循环，重新检查锁。如果锁已经被新来的线程拿走，它还得再次排队。因此这里必须用循环，不能醒来就直接进入临界区。

这种写法能保证互斥，但排队的线程可能反复抢不到锁，出现饥饿，也会增加唤醒和切换的开销。

`Mutex2` 有等待者时保持 `locked = true`，把锁直接交给队首线程。它从阻塞处返回时已经拿到锁，新线程不能插队。只有等待队列为空时，解锁才会把 `locked` 清为 `false`。

两套写法不能混用。解锁时清了 `locked`，等待者醒来后却不检查，就可能和新线程同时进入临界区。若解锁时保留 `locked = true`，等待者醒来又循环检查，它会认为锁还被占用，再次阻塞，最后没人能解锁。
